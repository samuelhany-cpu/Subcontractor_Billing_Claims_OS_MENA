# CAT-001 — Categories and subcategories vertical slice

## Outcome

CAT-001 implements CAT-001 through CAT-005 and the category-mutation portions of AUD-001 through AUD-003 across shared contracts, the NestJS API, isolated PostgreSQL tests, and the Arabic RTL settings interface. No later business module was implemented.

## Approved API contract

The owner approved and the OpenAPI contract now defines these `/api/v1` routes:

- `GET /categories?status=ACTIVE|INACTIVE|ALL` (`ACTIVE` by default).
- `POST /categories`.
- `PATCH /categories/{categoryId}` for name only.
- `POST /categories/reorder` with the complete active/inactive ID list.
- `POST /categories/{categoryId}/deactivate`.
- `POST /categories/{categoryId}/reactivate`.
- `POST /categories/{categoryId}/subcategories`.
- `POST /categories/{categoryId}/subcategories/reorder` with every child ID.
- `PATCH /subcategories/{subcategoryId}` for name only.
- `POST /subcategories/{subcategoryId}/deactivate`.
- `POST /subcategories/{subcategoryId}/reactivate`.

No hard-delete endpoint exists.

## Backend boundaries and persistence

`CategoriesModule` contains thin category/subcategory controllers, a bounded application service, a Prisma-specific repository, response mapping, validation, standardized errors, and tests. Public responses use shared contracts rather than Prisma records.

Names are trimmed, required, and limited to the committed 120-character database width. Category names retain the committed global uniqueness rule; subcategory names remain unique only within their parent. New records are active. Initial ordering uses the current maximum `sortOrder` plus one inside the mutation transaction.

Listing uses one bounded Prisma query with ordered nested subcategories. It does not query Expense, calculate usage/totals, or use Redis. The status filter applies to parent categories; each returned tree includes every active and inactive child with explicit state, ordered by `sortOrder` then ID. This makes settings/history complete while the shared selection helper applies effective activity separately.

## Ordering and concurrency

Both reorder operations accept complete lists only. Runtime contracts reject duplicate IDs. Application validation rejects missing, unknown, extra, or foreign-parent IDs before any update. Sort values become consecutive zero-based integers.

Reorder runs in a serializable Prisma transaction. P2034 serialization conflicts are retried up to three times. A concurrent create can therefore cause a retried stale complete list to fail validation instead of silently losing the new record. Updates and the compact audit event commit atomically. The UI exposes keyboard/touch buttons for moving up/down, prevents concurrent actions, and refreshes the authoritative server order after either success or failure. Global category ordering controls are enabled only in the `ALL` view because the approved payload must include inactive categories too.

## Activation semantics

Deactivate/reactivate are explicit operations and repeated transitions return 409. Deactivation never deletes or replaces a row, nulls an Expense reference, or changes child state. An inactive category and all its children are effectively unavailable for future manual classification, regardless of each child's stored `isActive`. An inactive child is also unavailable. Reactivation preserves identity and order and does not mutate children.

Creating or renaming a child under an inactive parent remains allowed as a reversible settings operation; effective selection still excludes it until the parent is active.

## Unclassified behavior

`Expense.categoryId` and `subcategoryId` remain nullable for import. No persisted `غير مصنف` row or seed is created. Shared `classificationDisplayName` maps null to `غير مصنف` for future display/report use, while `toClassificationOptions` returns only active categories and active children of active parents. Rename/deactivation preserve historical identifiers.

## Audit behavior

Create uses `AuditAction.CREATE`; rename, reorder, deactivate, and reactivate use the owner-approved `AuditAction.UPDATE`. Every payload includes an explicit operation name. Entity IDs, `RecordSource.WEB`, safe before/after state, and correlation IDs are stored. Reorder history contains compact before/after ordered ID arrays rather than large category trees.

Every mutation and audit append use the same Prisma transaction. No-op rename/reorder writes neither misleading mutation nor audit event. The immutable CORE-001 database trigger remains enabled.

## Web interface

`/settings/categories` provides Arabic-only active/inactive/all views, create/rename, explicit deactivate/reactivate, ordered category trees, subcategory management, empty/loading/API-error/mutation states, confirmation wording that explains retention, and accessible up/down controls. The application header now links to `المشروعات` and `الإعدادات`. Layout remains RTL, light, responsive, keyboard accessible, and uses large mobile controls.

The settings page explains unclassified import behavior without presenting `غير مصنف` as an editable category. It creates no data on initial load.

## Database and scope

Migration created: No. `apps/api/prisma/schema.prisma`, `docs/schemas/schema.prisma`, and existing migration history are unchanged. CORE-001 uniqueness, indexes, nullable import classification, and restrictive foreign keys were reused.

No category seed, expense service, report query, payee/agreement, transfer, dashboard, import, Telegram/n8n, backup, authentication, user, tenant, RBAC, tax, Claims, or accounting implementation was added.
