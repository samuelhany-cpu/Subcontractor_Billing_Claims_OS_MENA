# TEL-001 — Automation API Phase 1

Status: VERIFIED — NOT DEPLOYED

The API has a provider-neutral Automation module for `ADD_EXPENSE` and
`ADD_TRANSFER` drafts. It uses the shared Zod contracts and existing Expense
and Transfer business services; no financial row is created before confirmation.

## Security and ownership

- Every Automation route requires `x-automation-secret`; comparison uses
  constant-time bytes after a length check.
- The configured server-side `TELEGRAM_ALLOWED_CHAT_ID` is the sole allowed
  chat identity. Draft creation rejects any other supplied chat ID.
- Get, confirm, and cancel query by both draft ID and the configured chat ID.
  A foreign draft is indistinguishable from a missing draft (HTTP 404).
- Request shape and intent payloads are validated before persistence and
  invalid input returns HTTP 400.

## Transaction strategy

Confirmation uses one PostgreSQL transaction. A conditional `updateMany`
claims a pending, unexpired, owner-scoped draft; trusted Expense/Transfer
creation, immutable result linkage, and the existing CREATE audit event then
commit together. PostgreSQL rollback returns the draft to `PENDING` if either
the financial or audit insert fails. A committed confirmation returns the
stored result on retry.

The migration `20261031010000_automation_draft_results` adds nullable
result-entity type and UUID fields. It was applied only to disposable test
databases in this phase; production has not been migrated or deployed.

## Boundaries

No Telegram gateway, n8n workflow, public endpoint, production migration, or
Villa Obour production-data change is included in this phase.

## Production deployment preparation

A pre-deployment PostgreSQL backup was restore-verified in a separate disposable
PostgreSQL container. The production Compose configuration references the
existing protected automation secret and allowed Telegram chat ID for the API,
without storing either value in source control. After explicit owner approval,
the additive result-link migration was applied and only the API container was
recreated. Post-deployment readiness, authorization, port-isolation, and
financial reconciliation checks passed; see the production readiness report.
