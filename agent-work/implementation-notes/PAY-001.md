# PAY-001 — Implementation notes

## Scope delivered

PAY-001 implements PAY-001 through PAY-009, AGR-001 through AGR-006, and the Payee/Agreement portions of AUD-001 through AUD-003. No Expense creation workflow, Transfer, attachment, report, dashboard, automation, backup, authentication, tenancy, or accounting feature was added.

## Approved API contract

All routes use the existing `/api/v1` prefix:

- `GET /payees?status=ACTIVE|INACTIVE|ALL&search=...`
- `POST /payees`
- `GET /payees/{payeeId}`
- `PATCH /payees/{payeeId}`
- `POST /payees/{payeeId}/deactivate`
- `POST /payees/{payeeId}/reactivate`
- `GET /projects/{projectId}/payees/{payeeId}/agreement`
- `POST /projects/{projectId}/payees/{payeeId}/agreement`
- `PATCH /projects/{projectId}/payees/{payeeId}/agreement`

The prior underspecified Agreement `PUT` upsert was removed from OpenAPI. Creation and update are distinct: duplicate creation is a conflict and update requires an existing Agreement. No hard-delete route exists. Payee names remain intentionally non-unique.

## Payee behavior

- Name and enum type are required; specialty, phone, company name, and notes are optional.
- Outer whitespace is trimmed. Empty optional strings normalize to `null`.
- All five committed types are supported.
- Search is a trimmed literal PostgreSQL substring over name, company name, phone, and specialty. It is not fuzzy and does not impose uniqueness.
- Listing defaults to active Payees and sorts by name then ID.
- Deactivation preserves identity, Expenses, Agreements, and audit history. Reactivation uses the same ID.
- A repeated activation transition returns `PAYEE_STATE_CONFLICT`.
- As a safe reversible implementation choice, Agreement mutation also requires an active Payee; historical data remains readable. This does not alter stored Agreements or Expenses.

## Paid totals and project inclusion

Only non-deleted Expenses assigned to the Payee contribute to paid totals. Transfers, opening balances, Agreement totals, text inference, and null-Payee Expenses do not contribute.

A Project appears in Payee detail only when an Agreement exists or at least one non-deleted Expense exists for the Project/Payee pair. A Project does not appear solely because of soft-deleted Expenses. Archived qualifying Projects remain visible.

Money is aggregated in PostgreSQL as Decimal and serialized at fixed scale two. No financial value passes through JavaScript `number`.

Expected bounded query behavior:

- Payee list/search: one Payee query plus one grouped Expense query for all returned Payees.
- Payee detail: Payee lookup, one Project query including scoped Agreements, and one grouped Expense query by Project.
- Agreement read: bounded Project, Payee, Agreement, and aggregate lookups; no Expense rows are loaded.
- Agreement mutations: bounded reads/writes inside one transaction; no per-Expense or per-Project loops.

No Redis caching was added. The committed `Expense(payeeId, projectId)` index supports the aggregate boundary; specialty search remains an intentionally unindexed small global-directory field because no schema change was approved.

## Agreement calculations

`totalAmount` is parsed as a positive exact `Decimal(18,2)`. Paid is derived from active Expenses, remaining is `totalAmount - paid`, and overpaid is `max(paid - totalAmount, 0)`. Negative remaining is preserved. None of these derived totals are persisted.

The web live preview uses integer cents with `BigInt`, not floating point. API values remain authoritative.

## Audit and state rules

Payee create/update/deactivate/reactivate and Agreement create/update append immutable audit events in the same Prisma transaction as their mutation. Snapshots identify the operation, preserve Decimal instances for safe string serialization, include correlation IDs when present, and contain no secrets. No-op profile or Agreement updates do not append misleading events.

Agreement writes use the existing `ProjectStateService.assertAcceptsWrites`; archived Projects return the existing standardized conflict. Agreement reads deliberately bypass the write guard so archived history remains readable.

## Web application

- `/payees`: Arabic RTL list, server-side search, active/inactive/all filters, exact global totals, create form, activation controls, empty/no-results/loading/error states.
- `/payees/[payeeId]`: profile editing, exact global total, qualifying Project summaries, Agreement creation/update, remaining and overpayment display, and archived read-only state.
- The main shell includes `الموردون والصنايعية`.
- The UI is Arabic-only, light, responsive, keyboard accessible, and contains no login/account or Expense creation controls.

## Database

The CORE-001 Prisma schema and migration are reused unchanged. No migration, schema edit, seed data, duplicate Payee uniqueness, derived column, or PayeeProject table was added.

## Deferred

Expense CRUD, Expense selection behavior, attachments, soft-delete APIs, recycle bin, audit viewer, Dashboard, Reports, Excel, Telegram/n8n, and Backup remain deferred. The next eligible bounded task is EXP-001.
