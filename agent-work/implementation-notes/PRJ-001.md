# PRJ-001 — Projects vertical slice

## Outcome

PRJ-001 implements requirements PRJ-001 through PRJ-007 and the project-mutation portions of AUD-001 through AUD-003 across the NestJS API, shared contracts, and the Arabic RTL Next.js application. No later domain module was implemented.

## API and module boundaries

`ProjectsModule` contains a thin controller, a project-specific repository, application service, exact totals query, response mapping, request validation, and a reusable project-state service. The implemented routes are:

- `GET /api/v1/projects?status=ACTIVE|ARCHIVED|ALL`
- `POST /api/v1/projects`
- `GET /api/v1/projects/{projectId}`
- `PATCH /api/v1/projects/{projectId}`
- `POST /api/v1/projects/{projectId}/archive`
- `POST /api/v1/projects/{projectId}/restore`
- `GET /api/v1/projects/{projectId}/dashboard`

The dashboard route is deliberately a minimal project-totals response. It contains no charts, category totals, payee totals, or recent activity.

Shared Zod contracts validate UUIDs, trimmed nonblank names, active/archived/all filters, signed Decimal(18,2)-compatible opening-balance strings, and real calendar date-only strings. Prisma records are mapped to stable public contracts; financial values are always strings and date-only values are serialized as `YYYY-MM-DD`.

## Mutations and state transitions

New projects are active with `archivedAt = null`. Opening balance may be omitted, positive, zero, or negative. Opening-balance date is independently optional and may be cleared on update.

Only name, opening balance, and opening-balance date are editable through PATCH. Archived projects reject edits until restored. Archive sets status to `ARCHIVED` and `archivedAt`; restore returns the same row to `ACTIVE` and clears `archivedAt`. There is no hard-delete route.

The API returns `409 Conflict` for repeated archive/restore transitions. This reversible behavior was selected because the product documents require a clear invalid-state behavior but do not choose idempotent success. A no-op update returns the current representation without writing a misleading audit event.

`ProjectStateService.assertAcceptsWrites` centralizes future write eligibility: active succeeds, archived returns the standardized conflict, and missing returns not found. It performs no authentication or authorization.

## Audit behavior

Create, meaningful update, archive, and restore execute the Project mutation and `AuditService.append` inside the same Prisma transaction. Normal API/web mutations use `RecordSource.WEB`; restore maps to the existing `AuditAction.UNARCHIVE` enum. Project ID and request correlation ID are stored. Before/after snapshots contain only meaningful project state, with opening balance serialized as a fixed string and date-only values kept stable. No audit update/delete API was introduced.

## Totals and query behavior

The exact formulas are implemented once in `ProjectTotalsService`:

- total incoming transfers: non-deleted Transfer sum.
- total expenses: non-deleted Expense sum.
- total funding: opening balance plus transfers.
- available balance: total funding minus expenses.
- expense count: non-deleted Expense count.

Prisma Decimal performs every calculation; no financial value crosses JavaScript `number`. Empty aggregates serialize as `0.00` and negative available balance remains negative.

Project listing uses one ordered Project query plus one grouped Expense aggregate and one grouped Transfer aggregate. Query count is therefore bounded at three regardless of row count, with no financial rows loaded into application memory and no Redis cache. Detail/summary uses one project lookup and the two aggregates. Existing project/date and project/deletedAt indexes are reused.

## Web application

The Next.js 16 App Router now provides `/projects` and `/projects/[projectId]`. The root route redirects to Projects. The shell and screens are Arabic-only, `lang="ar"`, RTL, light mode, responsive, keyboard accessible, and use large touch targets.

The Projects page includes active/archived/all filtering, create form, exact decimal and date inputs, empty states, totals, archive confirmation that explains record retention, restore actions, and archived read-only marking. Project detail contains the six required summary measures and allows editing only while active. Loading, API failure/retry, validation, duplicate-name, not-found, mutation failure, archive, and restore states are handled without exposing internal errors.

The project selector is in the application header, lists active projects, follows the URL as authoritative context, handles zero active projects, links to archived projects, and does not persist authoritative selection data.

Server Components fetch data and Server Actions perform mutations, so browser code does not receive database credentials and mutation calls remain same-origin to the Next application. The API continues to create and propagate correlation IDs.

## OpenAPI synchronization

The active OpenAPI Project paths now define request/response schemas, `ALL`, project totals, the minimal dashboard, RFC 7807 responses, and a signed-money schema specifically for opening balance/funding/balance. The existing nonnegative Money contract remains available for later positive transaction amounts.

## Database and reversible decisions

No migration or Prisma-schema change was needed. CORE-001 already supports every project requirement.

Reversible implementation choices:

- no status query means `ALL` at the API; the Projects UI intentionally opens on active projects.
- deterministic sorting is name ascending, then UUID.
- repeated archive/restore returns 409.
- Next Server Actions are the mutation boundary; no browser API proxy or local selection persistence was added.
- shared contracts build as CommonJS so Nest runtime validation and Next bundling consume one package safely.
