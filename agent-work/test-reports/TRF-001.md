## Verified Scenarios

1. **Transfer Creation**: Validates required `projectId`, `transferDate`, positive 2-decimal string `amount`. Server assigns `source = WEB`. Transactional `AuditEvent` created.
2. **Transfer List & Filters**: Status filters (`ACTIVE`, `DELETED`, `ALL`), inclusive date range, pagination, deterministic sorting (`NEWEST` / `OLDEST`).
3. **Transfer Update**: Updates `amount` or `transferDate`. Immutable `projectId` and `source`. No-op update produces no `AuditEvent`.
4. **Soft Delete & Restore**: Soft-delete (`POST /transfers/{id}/delete`) sets `deletedAt`, removes transfer from active funding totals, appends `AuditEvent`. Restore (`POST /transfers/{id}/restore`) clears `deletedAt`, returns transfer to active funding totals, appends `AuditEvent`.
5. **Project Archive Guard**: All mutations (`create`, `update`, `delete`, `restore`) on archived projects return `409 Conflict`. Read actions remain available.
6. **Project Funding Calculations**:
   - `totalIncomingTransfers = sum(Active Transfers)`
   - `totalFunding = openingBalance + totalIncomingTransfers`
   - `availableBalance = totalFunding - totalExpenses`
7. **Arabic RTL Frontend**: Form validation, active-only project dropdowns, `dir="ltr"` monetary input fields, status filter controls, soft-delete confirmation modal, restore actions.
